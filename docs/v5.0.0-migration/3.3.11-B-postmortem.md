## What worked

### Sub-dispatch boundaries at commit-aligned bundle edges

3.3.11-B was originally scoped as a single brief. The first dispatch
attempt (dispatch-1) hit a legit scope-vs-context blocker mid-flight
and surfaced the catastrophic mid-flight-state risk. The orchestrator
then decomposed the brief into B.1 / B.2 / B.2.5 / B.3 at natural
bundle boundaries:

- B.1: dep bump + BQueue extraction + shared.nim creation.
- B.2: `{.error.}` cardinality gates (Bundle E) + typestate audit
  (Bundle G KEEP/DELETE).
- B.2.5: Queue reshape + UnboundedSipsic absorption + smart-ctor
  reduction + unbounded_sipsic.nim deletion (Bundles C + D + G).
- B.3: bench rewire + should_fail expansion + docs reconciliation +
  partial R-checks (Bundle F + L + tag deferred to B.4).

Each sub-dispatch closed with its own commit and left the worktree
green. No bundle spans a sub-dispatch boundary. This pattern was
successful: every dispatch reached a coherent end-state and was
recoverable.

Lesson: when a brief's scope crosses two cognitive units (e.g., type
reshape AND typestate attachment AND CHANGELOG AND bench delta),
pre-decompose into sub-dispatches at commit-aligned bundle boundaries
rather than dispatching the whole as a single unit and hoping the
subagent surfaces correctly mid-flight.

### M4 / M5 / M7 / M8 pepper antennae

The brief carried four pepper antennae that landed cleanly:

- **M4 (alias-return lock):** smart constructors return the
  user-visible alias (`BQueue`/`Queue`), never the backing type. The
  thin wrappers (`newSipsicQueue` etc.) honored this throughout.
- **M5 (R9 diagnostic-surface naming):** every `{.error.}` string
  references the user-visible alias name; zero `*Multi`/`*Single`
  leakage in error strings. The grep at end of B.3 confirms.
- **M7 (CHANGELOG worked example):** the v5.0.0 reshape addendum
  carries two worked examples — primary surface
  (`newBQueue`/`newQueue`) and two-type alias dispatch (reserved for
  Bundle F). Positions the two-ctor surface as canonical for new
  code; family wrappers as convenience aliases.
- **M8 (family-level should_fail coverage):** four new should_fail
  cases proving the Bundle E `{.error.}` gates fire through the
  thin-wrappers. NOT one case per individual wrapper (would have
  been 11); the family-level proof is sufficient because all
  wrappers delegate to the same underlying `{.error.}` overload.

Lesson: pepper antennae are durable across sub-dispatches when they
are pinned to LOCKED enforcement points (grep gates, return-type
locks, structural patterns). They survive context handoffs in a way
that prose guidance does not.

## What hurt

### Bundle F's scope was underestimated

The 3.3.11-B brief allocated Bundle F as one bullet in the same
sub-dispatch (B.3) as Bundles H/I/J/K/L/M. In practice, Bundle F
(Lifecycle + Claim-state typestates with two-type alias dispatch,
F.3.5 deliberate-negative test, M5 R9 enforcement, CFG analyzer
compliance across the entire push/pop/getProducer/getConsumer surface)
is a conceptually heavy piece on par with B.2.5's Queue reshape — and
B.2.5 itself had to be split off as its own sub-dispatch when
dispatch-1 surfaced as a blocker.

The B.3 implementer landed Bundles H/I/J/K-partial/M and surfaced
Bundle F + Bundle K-cold-state-bench-delta + Bundle L-postmortem
(this doc, light touch) + the local `v5.0.0` tag as the legitimate
B.4 follow-up dispatch, applying the same "surface rather than
commit half-state" pattern that B.2 used.

Lesson: Bundles F and B.2.5 are the same weight class. Bundle F
should have been its own sub-dispatch from the start. Future briefs
that touch typestate attachment surfaces should budget the
attachment-pragma layer as its own sub-dispatch independent of any
co-changes to the surrounding push/pop signatures.

### M6 reconciliation moved during execution

Bundle H2 (proactive bench-binary split for `bench_spsc` /
`bench_mpsc`) was specified in the brief as a "promoted from deferred
sub-question per most-correct-least-deferred" item. The B.3
implementer audited the pre-state and found the topology M6 was
trying to prevent (bounded+unbounded co-compilation in a single
binary) does NOT actually occur post-restructure: `bench_spsc` and
`bench_mpsc` are exclusively bounded (BQueue-only), and the unbounded
binaries are separate (`bench_unbounded_*`). The proactive split was
moot. Final state: 9 NIM_BINARIES (unchanged from `2ddca6a`).

Lesson: M6-style "preventive infrastructure" items deserve a brief
empirical audit BEFORE the implementer starts writing the split. The
audit cost is one grep + one `nimble c --compileOnly` per binary;
the cost of splitting prematurely is double the bench binary count
and a permanent CI matrix expansion.

### nimble vnext dep resolution fragility

`nimble should_fail` and `nimble test` fail to resolve dependencies
because the vnext SAT solver cannot find a published `typestates
>= 0.9.3`. The path-override in `config.nims` works for direct
`nim r --path:src` invocations but the `nimble` task driver tries to
re-resolve through the registry first. This is not a 3.3.11-B
regression — it pre-dates the sub-dispatch — but it forced the B.3
implementer to invoke runners directly via `nim r` rather than
through nimble. The R-check matrix in this dispatch was verified via
direct `nim r` invocations, not the `nimble test` task.

Lesson: when path-overrides target unpublished packages, document
the `nim r` fallback invocations alongside the `nimble` task entries
in the AGENTS.md / contributing docs.

## #9 paper-design-endorsement-without-empirical-probe (3 occurrences)

Distinct from #5, this failure mode fires when a brief author
endorses a design on paper without an empirical probe of the target
toolchain. Three occurrences in the v5.0.0 wave:

1. **M1 two-type alias dispatch** — the original Bundle F brief
   prescribed
   `type BQueueProducer*[T, ccCons, ccProd, ...] = when ccProd is ccMulti: BQueueProducerMulti[...] else: BQueueProducerSingle[...]`.
   On paper this matches the typestates v0.9.3 attachment-pragma
   surface. In practice, typestates 0.9.3's `{.attach.}` pragma on
   a `when`-branched type alias does not resolve correctly at
   instantiation time — the pragma is processed once on the alias,
   not per branch. Wall 2 fix in B.4.1.6 abandoned the two-type
   alias in favor of a single object type with internal `when`
   switch on the optional `claimed: bool` field.

2. **B.4.1 walls (self-loop + post-terminal)** — paper design said
   "Wall 1: every state-preserving method declares
   `{.transition: BQueueInit -> BQueueInit.}` so the typestate
   verifier accepts them as state-preserving." Empirically,
   typestates v0.9.3's
   `validateTransitionsRespectInitialTerminal` rejects self-loop
   transitions on initial states. Similarly Wall 3 ("the destructor
   transition catches use-after-destroy") — paper claim, but the
   CFG analyzer only checks reaches-terminal, not no-method-calls-
   in-terminal. Empirical probe (B.4.1.5) confirmed both walls;
   recovery was the Wall 1 and Wall 3 documented limitations.

3. **M3 pragma surface ambiguity** — the original 3.3.11-A brief
   used `{.transition(transitionError: "msg").}` (kwarg-in-call
   form) by analogy with `{.destructorTransition(T -> U).}`.
   Empirically, Nim's pragma parser rejects this form for
   typestates-introduced pragmas because the kwarg-in-call path
   isn't extended to handle non-built-in pragma names. Working
   form is the sibling pragma block:
   `{.transition, transitionError: "msg".}`. The M3 case is
   especially insidious because BOTH forms look like idiomatic
   Nim pragma syntax; the only signal is a compile-time "invalid
   pragma" error. Draft postmortem at
   `/tmp/m3-pragma-surface-postmortem-draft.md` to land in
   nim-typestates repo via separate dispatch (task #119, not part
   of B.4.2).

**Antidote: probe-at-brief-review-time.** For any brief that
prescribes a syntax form against a tool the author hasn't
recently empirically tested, the brief reviewer should pre-write a
3-line throwaway probe and compile-only it. Binary signal in
under 30 seconds. The cost of this discipline is one grep + one
`nim c --compileOnly` per prescribed-syntax claim; the cost of
skipping is one or more implementation attempts that surface as
blockers at the typestate-attachment layer. B.4.1.5 is the worked
example of recovering by adding the missing probe step
retroactively.

## Three-wall recovery chain — the empirical-probe pattern worked

B.4.1 → B.4.1.5 → B.4.1.6 is the canonical worked example of the
recovery pattern. Sequence:

1. **B.4.1 implementation attempt** — paper design fails at three
   walls (self-loop transitions, two-type alias dispatch,
   post-terminal CFG). Implementer surfaces all three as blockers
   rather than guessing at fixes. Wall 3 in particular is a
   "documented limitation" — the design assumed v0.9.3 would catch
   use-after-destroy and it doesn't.

2. **B.4.1.5 empirical probe** — dispatched read-only with three
   probe scenarios mapping 1:1 to the three walls. Probes confirm:
   (a) self-loop transitions ARE rejected → no-self-loop pattern
   needed; (b) `when`-branched type aliases on `{.attach.}` DO NOT
   work → single-object-with-internal-when pattern needed; (c) CFG
   analyzer DOES NOT catch use-after-destroy → documented
   limitation with recovery pointers (typestates v0.10+ post-
   terminal CFG mode OR consume-on-transition destructor pattern).

3. **B.4.1.6 implementation under probe-validated design** —
   single atomic commit. No further surfaces. 240/240 across all 5
   MM lanes, should_fail 14/14, R7/R8/R9 clean.

Total cost of the three-wall chain: 3 dispatches (1 surfacing +
1 probe + 1 implementation). Cost without the probe pattern:
N dispatches where N is the number of mid-flight surface-and-
retry cycles before the implementer empirically discovers all
three walls in sequence. Probe-before-implementation strictly
dominates surface-and-retry once N ≥ 2.

## Personal #3 calibration — reference-implementation enumeration

Bundle F's Wall 3 documentation references nim-debra's
`pinned_scope.nim:128-131` as the recovery pattern for
must-not-double-use sites. The reference implementations the
v5.0.0 wave drew from are:

- **`debra/pinned_scope.nim` PinnedScope** — consume-on-transition
  destructor pattern. `=destroy(s)` sets `consumed = true` and
  emits the destructor transition; any subsequent method call
  checks `doAssert(not consumed, "...")` (lines 128-131). The
  v5.0.0 wave references this pattern but does NOT adopt it
  blanket-style on BQueue/Queue because the runtime check would
  inject a branch on every push/pop.
- **`debra/pinned_scope.nim` EpochGuardContext** — pin-claim /
  pin-release lifecycle with destructor-terminated transition.
  Reference for the BQueue Lifecycle pattern (`BQueueInit ->
  BQueueDestroyed`); the v5.0.0 BQueue Lifecycle is the same
  shape with `=destroy` driving the terminal transition.
- **`typestates v0.9.3` `pkUnmarked` registration path** — the
  brief assumed this path was live for cross-module
  `{.transition.}` rejection. Empirically (B.4.1.6 deviation #3)
  this path is dead code; the real rejection happens via
  `pragmas.nim:742-751`. Recovery: F.3.5 cross-module test
  exercises the live `{.transition.}` rejection path with the
  expected diagnostic substring `"notATransition"` still in
  the hint text.

**Behavior-vs-mechanism framing** (per pepper's checkin-0031
calibration). The wave repeatedly conflated behavior ("the
typestate catches use-after-destroy") with mechanism ("the
attachment pragma + destructorTransition handle this"). Each
#9 occurrence was a behavior claim that didn't survive empirical
contact with the mechanism. Calibration: when a brief makes a
behavior claim about a tool feature, the reviewer should
mechanically translate it to "this means X is in the tool's
verifier path", then probe whether X is actually in the
verifier path. Behavior claims without mechanism translation
are #9 risk regardless of how plausible the claim is on its face.

## Deviations log — Bundle F (B.4.1.6)

Three deviations from the brief landed in the B.4.1.6 commit and
warrant explicit retrospective notation:

1. **`./internal/typestates_dsl.nim` shim** (deviation #1). The
   brief implicitly assumed `bqueue.nim` and `queue.nim` could
   `import typestates` directly to pull the upstream package's
   `typestate` / `destructorTransition` DSL macros. Empirically,
   Nim's module resolution prefers a same-directory sibling over a
   `--path:`-resolved package. The local
   `lockfreequeues/typestates.nim` (re-export module) shares the
   unqualified name `typestates`, so an unqualified
   `import typestates` from `bqueue.nim` resolves to the local
   sibling (which only re-exports internal state types, NOT the
   upstream DSL). The shim is a 4-line module under `./internal/`
   that does `import typestates; export typestates` — from
   `./internal/`, the local re-export module is not a sibling, so
   the upstream package wins resolution. Both consumer modules
   then `import ./internal/typestates_dsl`. Documented in the
   shim's header.

2. **`QC`-prefix for queue Claim-state types** (deviation #2).
   Bundle F's BQueue uses `Unclaimed` / `ProducerClaimed` /
   `ConsumerClaimed` / `BothClaimed`. The unbounded Queue's
   Claim-state state-types use a `QC` prefix (`QCUnclaimed` /
   `QCProducerClaimed` / `QCConsumerClaimed` / `QCBothClaimed`) to
   avoid the same-name typestate attachment limitation (typestates
   v0.9.3 emits a `[User]` warning when an attached typestate
   shares the type-name of a state — see the existing
   `VirtualValueN` / `CASAttempt` warnings already in the build
   log). Disambiguating queue-side Claim-state names also reads
   better at call sites where both BQueue and Queue Claim-state
   state-types may be visible via the lockfreequeues aggregator.

3. **F.3.5 cross-module test exercises `{.transition.}` rejection,
   not unmarked-proc rejection** (deviation #3). The brief
   referenced `verify.nim:2069-2074` ("external modules must use
   `{.notATransition.}` for procs on typestate states").
   Empirically, the `pkUnmarked` registration path is dead code in
   typestates v0.9.3 — the verifier only catches the cross-module
   case via the `{.transition.}` pragma's own check at
   `pragmas.nim:742-751` ("Cannot define transition on typestate
   '...' from external module."). The F.3.5 test exercises THAT
   check instead. The brief's hint text (`"Use {.notATransition.}"`)
   still appears in the diagnostic, so the substring assertion
   `"notATransition"` lands on real verifier output.

## M9 audit — 4 deleted doAsserts

The master brief's M9 antenna called for a 5-minute audit of "4
deleted `static doAssert`s from B.2.5's `t_queue_type_shell.nim`
consolidation" (test count 244 → 240).

**Finding**: the literal `doAssert` count in the v5.0.0 wave diff
shows zero non-layout `doAssert` deletions in tests/, and src/
layout-assert deletions are 1:1 paired with replacement layout
asserts on the new BQueue shape (from the deleted per-family
mupmuc/mupsic/sipmuc layout blocks to the BQueue 6-param layout
block). The "4 deleted doAsserts" figure does not map literally
to a `doAssert` count in the wave's diff.

What the M9 figure DOES map to is the 9-static-assert
`assertQueueParams` suite in the pre-B.2.5 `t_queue_type_shell.nim`
file. Of the 9 Doc C §3.0.2.4 param-coherence guards in that
suite, the B.2.5 reshape from 10-param `Queue` to 6-param
`BQueue` + 6-param `Queue` made the cross-axis guards
**type-impossible** rather than enforced-by-static-assert:

- Guards that mapped to "ccMulti requires P > 0" / "ccMulti
  requires C > 0" became per-cardinality `when` branches in the
  BQueue/Queue field layout (the `cells: array[N, ...]` field
  is only present under `when ccProd == ccMulti or ccCons ==
  ccMulti:`, structurally collapsing the cardinality-P/C
  coherence guard).
- Guards that mapped to "rkEbr requires MaxThreads > 0" became
  the `MaxThreads: static int` param on the unbounded Queue
  shape with the manager / pin-claim fields under the
  reclamation `when` branch.

Per the M9 antenna's success criteria ("If 4/4 redundancy proven:
positive postmortem item — 'type split organically eliminated 4
runtime-static guards by making the constraints type-impossible.'"),
this lands as a **positive postmortem item**: the BQueue/Queue
type split organically eliminated approximately 4 of the 9 Doc C
guards by making the constrained shapes type-impossible. The
remaining 5 guards (intra-axis shape constraints like "N is a
power of two", "S > 0", "MaxThreads > 0") remain as
compile-time checks in `bqueue.nim` and `queue.nim` either as
explicit `static:` blocks or as `static int` param constraints
in the type signature.

## M10 audit — UnboundedSipsic deprecation stub

The master brief's M10 antenna called for an optional
`type UnboundedSipsic = object` with `{.error: "...".}` for
backwards-compat one-line guidance ("provides a useful compile
error instead of Nim's unhelpful 'undeclared identifier'").

**Decision: SKIP, with rationale**. Two reasons:

1. **Surface-leak ambiguity.** Adding a `type UnboundedSipsic =
   object` (even with `{.error.}`) leaks the legacy identifier
   back into the v5.0.0 public namespace. Tooling (IDE
   completion, grep workflows) would see `UnboundedSipsic` in
   the umbrella module and treat it as a current type, despite
   the `{.error.}` pragma. The CHANGELOG breaking-change
   banner + `newUnboundedSipsicQueue` smart constructor already
   provide the migration path.

2. **Generic-parameter mismatch.** Users who write
   `UnboundedSipsic[S, T]` (with generic params, matching the
   pre-v5.0.0 signature) would hit a generic-instantiation
   error against the parameter-less stub, NOT the `{.error.}`
   message. Honoring the original two-param signature
   (`type UnboundedSipsic[S: static int, T] = object`) only to
   carry an error pragma is more API-surface complexity than
   one-line guidance warrants.

Recovery: the migration doc at
`docs/v5.0.0-migration/3.3.11-B-final-shape.md` and the v5.0.0
CHANGELOG entry's BREAKING section already document the
absorption with the explicit `newUnboundedSipsicQueue` call-site
guidance. Users encountering "undeclared identifier:
'UnboundedSipsic'" on a v4.x-to-v5.0.0 migration have those two
documents as the canonical recovery surface.

## Stress-test triage — drop with documented rationale

`nimble stresstests` was broken on the B.4.1.6 baseline
(`e99bdf7`, pre-Bundle-F): the 9 `stress-tests/t_*_threaded.nim`
files referenced undeclared `Mupmuc`, `Sipmuc`, `Mupsic`, `Sipsic`,
`UnboundedMupmuc`, `UnboundedMupsic`, `UnboundedSipmuc`,
`UnboundedSipsic` types — the legacy per-family aliases deleted
by the v5.0.0 reshape. The breakage predates B.4.1.6; B.4.1.6
verified by stashing changes and re-testing on bare baseline.

**Decision: DROP**. Rationale:

1197 LOC across 9 stress test files, all using the legacy
4-param family type signatures (`Mupmuc[N, P, C, T]`,
`Mupsic[N, P, T]`, etc.) and pre-DEBRA constructors. Rewiring to
the new BQueue/Queue surface requires:

- Per-file type signature migration (8 files × ~30-60 min each).
- New `attach` / `detach` call-site pattern for ccMulti
  producers / consumers (4 view types × per-stress-shape adaptation).
- `MaxThreads` plumbing for the unbounded variants (4 files).
- New `getProducer()` / `getConsumer()` semantics under
  Claim-state typestates (single-claim-per-handle vs the legacy
  `getProducer(idx)` multi-index idiom).

Conservative estimate: 4-6 hours. The v5.0.0 wrap-up budget for
B.4.2 is 3-4 hours total covering bench delta + audits + tag.
Rewiring stress-tests would consume the entire wrap-up budget on
a single sub-item; the bench delta + tag would have to defer to
a B.4.2.5 continuation. That is the wrong cost-distribution
tradeoff.

Per Bundle I principle ("do NOT silently disable failing tests —
fix production code OR delete the test"), the stress test suite
+ `stresstests` nimble task are deleted in B.4.2. The MM lane
matrix (5 lanes × 240 tests at maximum stress shape, plus
TSan/ASan sanitizers) provides primary concurrency-correctness
signal; the dropped suite was duplicative single-shape coverage.

Recovery for post-v5.0.0: if a coverage gap surfaces under field
use, a smaller targeted stress suite can be added against the
new BQueue/Queue surface with the attach/detach Claim-state
idiom. The scope of a resurrected suite would naturally narrow
to the shapes the MM lane matrix can't exercise (e.g., long-
duration soak under `LFQ_STRESS_DURATION_SEC`) rather than
mirroring the 9-file pre-v5.0.0 topology.

## Cold-state bench delta — methodology and outcome

Per the operator's durable
`feedback_thermal_throttling_validation.md` rule, back-to-back
compile runs on Apple Silicon throttle 4-5× and bias wall-clock
measurements. B.4.2 honored the cold-state preconditions:

1. **5-minute idle gap before the first bench binary's compile
   + run**. `pmset -g therm` reported "No thermal warning level
   has been recorded" continuously across the gap.
2. **Per-binary thermal recheck**. Between bench binaries, the
   runner waited 30s settle and re-checked `pmset -g therm`
   before launching the next binary. All 9 runs were under
   "no thermal warning recorded".
3. **Compile per the prior bench methodology**: `nim c -d:release
   --threads:on benchmarks/nim/<binary>.nim` (mirrors the
   `lockfreequeues.nimble benchmarks` task).
4. **Baseline JSON**:
   `benchmarks/results/v5.0.0-final-3.3.9-D.json` (pre-Bundle-F
   3.3.9-D state).
5. **Post JSON**: per-binary fragments merged into
   `benchmarks/results/v5.0.0-bench-delta.md` summary report.

See `benchmarks/results/v5.0.0-bench-delta.md` for the full
per-slug delta table, outlier list, and summary statistics. The
binary-size delta is captured in the same file plus the v5.0.0
CHANGELOG "Refactor highlights" section.
