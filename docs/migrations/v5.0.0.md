# v5.0.0 — Static Thread Affinity Endpoint API

v5.0.0 is a wholesale replacement of the per-thread view types
(`BQueueProducer` / `BQueueConsumer` / `QueueProducer` / `QueueConsumer`)
with a single typestate-checked `Unbound → Bound → Closed` endpoint
lifecycle. The new surface enforces thread-affinity discipline at
**compile time** via the typestate FSM + role-discriminating effect
tags + a debug-mode `getThreadId()` backstop.

This is a breaking change with no compatibility shim. Existing v4.x
callers must migrate.

## What changed

- **New endpoint types** in `lockfreequeues/endpoint`:
  - `Unbound[T, Tag, queueT]` — endpoint reserved on a queue but not
    yet bound to a thread.
  - `Bound[T, Tag, queueT]` — endpoint bound to the calling thread;
    the ONLY type on which `push` / `pop` are defined.
  - `Closed[T, Tag, queueT]` — released endpoint (alias for
    `EndpointClosed`; the longer name avoids a typestate-state name
    collision with debra's `EpochGuardContext.Closed`).
- **Lifecycle transitions**:
  - `bindToThread(u: sink Unbound): Bound` — moves the endpoint into
    the `Bound` state on the calling thread; for Queue endpoints,
    registers with the debra manager.
  - `close(b: sink Bound): Closed` — terminal transition; for Queue
    endpoints, unregisters from the debra manager.
- **Factories** in `lockfreequeues/endpoint`:
  - `getProducer(q: var BQueue/Queue)` and
    `getConsumer(q: var BQueue/Queue)` — return `Unbound[T,
    AnyThreadTag, queueT]`. Caller must `bindToThread()` before any
    `push`/`pop`.
  - `getProducerHere(q)` / `getConsumerHere(q)` — sugar: `getProducer
    + bindToThread` in one call (same-thread shortcut).
  - `bindConsumer(q: var Queue[T, ccProd, ccSingle, …])` — one-shot
    bind for the single consumer of an MPSC queue (replaces v4.x
    `attachConsumer`).
- **Role discrimination** via `Tag` generic + effect-tag pragmas (see
  `lockfreequeues/role_tags`):
  - `AnyThreadTag` — same-thread shortcut path (no per-spawn discipline).
  - `SpscProducerTag` / `SpscConsumerTag` — SPSC role tags.
  - `MpmcProducerTag` / `MpmcConsumerTag` — MPMC role tags (also cover
    MPSC producer / SPMC consumer roles per design Option A).
- **`push` / `pop` constrained on Tag**:
  - `push*[…; Tag: SpscProducerTag | MpmcProducerTag | AnyThreadTag](
    self: var Bound[T, Tag, queueT], …)` — rejects consumer tags at
    the proc signature.
  - `pop*[…; Tag: SpscConsumerTag | MpmcConsumerTag | AnyThreadTag](
    self: var Bound[T, Tag, queueT])` — rejects producer tags.
- **DELETED** (with no shim): `BQueueProducer`, `BQueueConsumer`,
  `QueueProducer`, `QueueConsumer`, `attach`, `detach`,
  `attachConsumer`, the per-view `BQueueClaimState` /
  `QueueClaimState` typestates, and their associated destructors.

For the Sipsic / Mupmuc / Sipmuc / Mupsic → Spsc / Mpmc / Spmc / Mpsc
rename that landed earlier in the v5.0.0 cycle, see `CHANGELOG.md`.

## Why the change

The runtime `getThreadId()` assertions used in v4.x caught thread-
affinity violations only at the call site that crossed the line.
v5.0.0 lifts that check into the type system: wrong-thread `push` is
a compile-time error, not a runtime defect. The four-layer
architecture composes typestates (lifecycle), effect tags (role), and
optional `{.experimental: "strictEffects".}` `{.forbids: […].}`
regions for static discipline.

See `docs/design/2026-05-28-static-thread-affinity-design.md` §2 for
the full motivation.

## Four-layer mental model

```
+---------------------------------------------------------------+
| Layer 4  std/typedthreads {.thread.} + Isolated handoff       |
+---------------------------------------------------------------+
| Layer 3  Spawn API: defineProducerWorker / defineConsumerWorker |
|          + spawnDefinedProducer / spawnDefinedConsumer (2-step) |
+---------------------------------------------------------------+
| Layer 2  Effect-tag role discrimination via {.tags: [Tag].}   |
|          Wrong-role tag fails at proc signature constraint    |
+---------------------------------------------------------------+
| Layer 1  Lifecycle typestate Unbound -> Bound -> Closed       |
|          push/pop only defined on Bound (compile error else)  |
+---------------------------------------------------------------+
```

## v4.x → v5.0.0 cookbook

### Same-thread producer (BQueue MPMC)

v4.x:
```nim
var q: BQueue[int, ccMulti, ccMulti, 1024, 8, 8]
var p = q.getProducer()
p.attach()
discard p.push(42)
```

v5.0.0:
```nim
var q = initBQueue[int, ccMulti, ccMulti, 1024, 8, 8]()
var bp = q.getProducerHere()  # AnyThreadTag, bound to this thread
discard bp.push(42)
```

### Cross-thread producer (worker thread does the push)

v4.x:
```nim
var p = q.getProducer()  # reserve slot from main
proc worker(_: int) {.thread.} =
  p.attach()             # register handle on worker thread
  discard p.push(42)
var thr: Thread[int]
createThread(thr, worker, 0)
joinThread(thr)
```

v5.0.0 (2-step spawn API):
```nim
import lockfreequeues/[bqueue, endpoint, role_tags, spawn]

# Worker declaration — MUST be at module scope:
defineProducerWorker(PushOnce, BQueue[int, ccMulti, ccMulti, 1024, 8, 8]):
  discard producer.push(42)  # `producer` injected as Bound[T, MpmcProducerTag, …]

proc main =
  var q = initBQueue[int, ccMulti, ccMulti, 1024, 8, 8]()
  var thr = spawnDefinedProducer(PushOnce, q)
  joinThread(thr)

main()
```

For per-call dynamic bodies (rare; usually a fixed worker pattern is
preferable), the manual `createThread` pattern also works:
```nim
type WorkArg = Unbound[int, MpmcProducerTag, typeof(q)]
proc worker(arg: WorkArg) {.thread, nimcall,
                            tags: [MpmcProducerTag, TypestateOp, RootEffect],
                            gcsafe.} =
  var u = arg
  var producer = u.bindToThread()
  discard producer.push(42)

let u = q.getProducer()
let tagged = WorkArg(queue: u.queue, idx: u.idx)
var thr: Thread[WorkArg]
createThread(thr, worker, tagged)
joinThread(thr)
```

### MPSC single consumer

v4.x:
```nim
var q = newUnboundedMpscQueue[int, stEager, 16, 4]()
q.attachConsumer()
let v = q.pop()
```

v5.0.0:
```nim
var q = newUnboundedMpscQueue[int, stEager, 16, 4]()
var bc = q.bindConsumer()   # one-shot reserve + bind
let v = bc.pop()
```

## MPMC asymmetry — Option A

Per design §4.1, all MPMC producers share `MpmcProducerTag` (no
per-spawn freshness) and all MPMC consumers share `MpmcConsumerTag`.
This means the type system distinguishes producer-side vs
consumer-side but does NOT distinguish individual producer threads
from each other. Per-thread identity is runtime-enforced via the
debug `getThreadId()` assertion in `push`/`pop` bodies.

## `strictEffects` opt-in for downstream

Downstream callers that want region-level role forbidding can enable:

```nim
{.experimental: "strictEffects".}
proc pureRegion(b: var Bound[int, SpscProducerTag, BQueue[…]])
    {.forbids: [SpscProducerTag].} =
  # Calling b.push() here is a compile-time error: push carries
  # SpscProducerTag in its effect set, which violates the forbids
  # region.
  discard
```

See `tests/should_fail/endpoint_forbids_region.nim` for the runnable
proof.

## Spawn API — 2-step instead of single-call macro

The originally-planned single-call macros `spawnBoundProducer(queue):
body` / `spawnBoundConsumer(queue): body` hit a Nim 2.2.10 codegen
issue: `{.thread, nimcall, gcsafe.}` procs emitted by macros or
templates in nested scope are silently downgraded to closures, and
`createThread` then calls into invalid memory at thread entry. The
2-step API shipped in v5.0.0 (`defineProducerWorker` +
`spawnDefinedProducer`) sidesteps this by making the module-scope
constraint EXPLICIT in the API shape.

**Module-scope constraint**: `defineProducerWorker` /
`defineConsumerWorker` MUST be invoked at module scope (like `proc`
/ `type` declarations). Putting them inside a `proc` body produces
the same nested-scope codegen failure as the single-call macro
would. v5.0.0 enforces this by convention + doc-comment; v5.0.1
follow-up: file the Nim upstream issue + add a static compile-time
guard if a Nim mechanism exists.

The single-call form may be collapsed back if the upstream codegen
issue is resolved; the `spawnBoundProducer` name is reserved for
that future.

## Nim version pin

v5.0.0 requires Nim ≥ 2.2.10. Earlier versions lack the typestates
0.12.0 / debra 0.9.0 compatibility surface.

## Dependencies

- `typestates >= 0.12.0` (was `0.10.0` in v4.x)
- `debra >= 0.9.0` (was `0.8.0` in v4.x; v0.9.0 adds CC-generic
  `unregisterThread` used by `endpoint.close` for Queue endpoints)

## Phase B — strict-LCRQ migration on unbounded MPMC

Late in the v5.0.0 cycle, the unbounded `Queue[T, ccMulti, ccMulti, …]`
arm was re-implemented on top of strict-LCRQ cells (LCRQ paper §4
close-CAS-on-empty progress guarantee). This is a second breaking
change inside the v5.0.0 wave, narrower than the endpoint-API migration
above but worth calling out separately because it constrains `T`.

### What changed

- The unbounded MPMC arm (`Queue[T, ccMulti, ccMulti, …]`) is now a
  strict-LCRQ queue. Each cell is `LCRQCell[T] = Atomic[Pair[uint, T]]`
  (a packed seq/payload pair manipulated via DWCAS).
- The close-CAS-on-empty progress rule from LCRQ paper §4 is honoured:
  consumers that observe an empty cell race to publish a `closed`
  sentinel, which resolves the case-(b) consumer-reservation race in
  the pop fast-path (Phase B design §5.3).
- BQueue is **unchanged**. The bounded MPMC arm continues to use
  Vyukov per-slot seq counters (single-word, no DWCAS), so it keeps
  move-only T, wide T, and (with `-d:allowNonLockFreeQueueItems`)
  ref T support.

### Breaking change

- `Queue[T, ccMulti, ccMulti, …]` now requires
  **`supportsCopyMem(T) AND sizeof(T) <= 8`** (8 bytes on 64-bit
  targets; 4 bytes on 32-bit targets — the limit is `sizeof(uint)`
  because the DWCAS payload lane is platform-native).
- Violations fire a compile-time `{.error.}` overload whose message
  cites the migration recipes below.
- No runtime shim; recompile is required.

### Migration recipes

**Recipe A — switch to `BQueue[T]` (bounded MPMC).** The most
mechanical migration when the producer is willing to accept
backpressure. `BQueue` preserves general T (move-only, wide value
types, ref T with the escape hatch flag). Trade-off: bounded
capacity instead of unbounded growth.

```nim
# Before (v4.x or earlier v5.0.0 cycle):
var q = newUnboundedMpmcQueue[Job, stEager, 64, 8]()

# After:
var q = newMpmcQueue[Job, 1024, 8, 8]()   # N=1024 slots, 8 producers, 8 consumers
```

**Recipe B — keep unbounded MPMC, store `ptr T`.** Preserves
strict-LCRQ progress guarantees and unbounded growth; adds one
pointer indirection. Allocator choice is the caller's: a plain
`create(T)` + `dispose` pair works for ownership-clear cases;
debra-managed allocation (the pattern in
`examples/job_scheduler.nim`) is preferred when reclamation must
itself be lock-free.

```nim
# Before:
var q = newUnboundedMpmcQueue[Job, stEager, 64, 8]()
q.push(job)                # T is Job (>8 bytes), rejected in Phase B

# After:
var q = newUnboundedMpmcQueue[ptr Job, stEager, 64, 8]()
let p = create(Job); p[] = job
q.push(p)                  # T is ptr Job (8 bytes), accepted
```

See `examples/job_scheduler.nim` for the canonical `ptr T` pattern
with worker threads. Anti-pattern: pushing `nil` for `T = ptr X` —
the primitive's `doAssert` will fire at runtime (the `Option[T]`
slot can't transport nil distinctly from "empty"). Always validate
non-nil before push.

**Recipe C — shrink T to ≤ `sizeof(uint)`.** Only works if the
payload is genuinely numeric- or pointer-sized: integer IDs,
file descriptors, small `distinct` integer wrappers, opaque
handles. If the type was already 8 bytes or smaller and trivially
copyable, no source change is required — just recompile against
v5.0.0.

### Why?

The LCRQ §4 close-CAS-on-empty progress rule requires an atomic CAS
over the `(seq, payload)` pair on every cell. The hardware DWCAS
primitive on 64-bit targets is 128 bits wide, which leaves exactly
`sizeof(uint)` (8 bytes) for the payload lane. Anything larger
either spills into a second word (defeating the per-cell DWCAS
contract) or requires a different concurrency protocol entirely.

`BQueue` stays general because Vyukov MPMC uses a single-word
sequence counter living **next to** (not packed with) the slot
data, so the slot can be an arbitrary value type without affecting
the atomic word width.
